## ADR-001: 타입과 유틸리티는 사용 범위에 따라 배치한다

- 날짜: 2026-10-01
- 상태: 대체 — [ADR-002](#adr-002-타입과-유틸리티를-별도-폴더로-분리한다)
- 범위: 모바일 앱의 직접 작성한 타입과 유틸리티

### 배경

지점찾기의 가격 표시 함수 `formatLocationPrice`를 `utils/price.ts`로, `LocationPoint` 타입을 `types/location.ts`로 분리해 관리하는 방안을 검토했다.

현재 `formatLocationPrice`는 지점 마커와 상세 화면에서 사용한다. 숫자의 원화 표기뿐 아니라 가격이 없을 때 `요금 문의`, 시작 가격에는 `원~`를 붙이는 지점 요금 표시 규칙을 포함한다.

`LocationPoint`는 지점찾기 컴포넌트와 해당 기능의 mock 데이터에서 사용한다. 여러 컴포넌트에서 사용하지만, 아직 서로 다른 기능에서 공유하는 타입은 아니다.

### 결정

1. **기능 전용 타입과 유틸리티는 `mobile/features/<feature>/` 가까이에 둔다.** 여러 컴포넌트가 사용하거나 `mocks/`에서 참조한다는 이유만으로 공용 폴더로 옮기지 않는다.
2. **서로 다른 기능에서 실제로 같은 타입이나 규칙을 공유할 때 공용 폴더로 옮긴다.** 공용 타입은 `mobile/types/`, 공용 유틸리티는 `mobile/utils/`에 둔다. 향후 재사용 가능성만으로 폴더를 미리 만들지 않는다.
3. **새로 만드는 타입·유틸리티 폴더 이름은 `types/`, `utils/`로 통일한다.** 공용 파일은 `location.ts`, `price.ts`처럼 다루는 대상을 드러내는 이름을 사용한다. 기능 내부에서는 기존 `types.ts`처럼 작은 단일 파일을 유지할 수 있고, 파일이 늘어나면 `types/`, `utils/`로 묶는다.
4. **유틸리티의 배치는 포함된 규칙을 기준으로 판단한다.** 숫자 포맷 함수라도 지점 전용 문구와 요금 정책이 포함되면 지점 기능에 둔다. 다른 기능의 가격 표기가 다르면 공통 숫자 포맷과 기능별 문구 처리를 분리할지 검토한다.

### 적용 현황

이번 결정은 배치 기준을 기록하며, 소스 파일 이동이나 import 변경은 수행하지 않는다.

| 대상 | 현재 위치 | 현재 결정 | 향후 분리 조건 |
| --- | --- | --- | --- |
| `formatLocationPrice` | `mobile/features/locations/formatLocationPrice.ts` | 지점 기능 안에 유지 | 기능 내부 유틸리티가 늘어나면 `features/locations/utils/price.ts`로 정리할 수 있다. 다른 기능에서도 동일한 규칙을 사용하면 `mobile/utils/price.ts`로 옮긴다. |
| `LocationPoint` | `mobile/features/locations/types.ts` | 현재 위치에 유지 | 예약·홈 등 다른 기능에서도 동일한 모델을 사용하면 `mobile/types/location.ts`로 옮긴다. |

위의 향후 경로는 배치 기준이며, 현재 생성된 파일이나 폴더가 아니다. API 연동 시 화면용 타입과 API 응답 타입이 같은 모델인지도 별도로 확인한다.

### 검토한 대안

| 대안 | 장점 | 현재 선택하지 않은 이유 |
| --- | --- | --- |
| 모든 타입과 함수를 처음부터 공용 `types/`, `utils/`에 배치 | 종류별로 파일을 찾기 쉽다. | 기능 전용 규칙과 실제 공용 코드가 섞이고, 관련 파일이 기능 밖으로 흩어진다. |
| 공유가 생겨도 각 기능에 계속 별도로 유지 | 각 기능을 독립적으로 수정하기 쉽다. | 실제로 같은 모델과 규칙을 공유할 때 중복 정의와 변경 누락이 생길 수 있다. |

### 영향

- 기능 구현과 관련 타입·규칙을 함께 찾고 수정하기 쉽다.
- 공용 폴더에는 실제 공유하는 코드가 모인다.
- 공유가 생기는 시점에는 파일 이동, 소비자의 import와 테스트 경로 변경, 구조 문서 갱신이 필요하다.
- 역할별 폴더만 보는 방식보다 파일 탐색 시 기능 이름을 먼저 알아야 한다.

### 재검토 조건

- 지점찾기 외의 기능에서 `LocationPoint` 또는 동일한 가격 표시 규칙을 사용한다.
- 한 기능의 타입·유틸리티 파일이 늘어나 내부 폴더로 묶을 필요가 생긴다.
- API 연동으로 데이터 계약과 화면용 모델의 책임을 구분해야 한다.
- 기능별로 같은 구현이 중복되거나, 공용 코드에 특정 기능의 조건 분기가 늘어난다.

## ADR-002: 타입과 유틸리티를 별도 폴더로 분리한다

- 날짜: 2026-10-01
- 상태: 채택
- 범위: 모바일 앱의 타입 전용 파일과 UI에 의존하지 않는 유틸리티 파일
- 대체: ADR-001

### 배경과 결정

사용자 요청에 따라 타입과 유틸리티 파일을 종류별로 찾을 수 있도록 `mobile/types/`와 `mobile/utils/`를 별도로 만든다. 폴더명은 기존 복수형 명명 기준을 유지한다. 기능 전용 규칙도 이 폴더에 배치하되, 파일명으로 대상을 구분한다. 폴더에 있다는 이유만으로 모든 기능에 동일한 규칙을 적용하지 않는다.

### 적용 현황

| 대상 | 이전 위치 | 새 위치 |
| --- | --- | --- |
| `LocationPoint` | `mobile/features/locations/types.ts` | `mobile/types/location.ts` |
| 지점 가격 표시 | `mobile/features/locations/formatLocationPrice.ts` | `mobile/utils/formatLocationPrice.ts` |
| 바텀 시트 높이 계산 | `mobile/components/ui/bottomSheetLayout.ts` | `mobile/utils/bottomSheetLayout.ts` |
| QR 밝기 세션·앱 상태 연결 | `mobile/features/access/brightnessSession.ts` | `mobile/utils/brightnessSession.ts` |

소비자의 import와 기존 테스트의 로딩 경로를 함께 변경한다. 컴포넌트 내부 props 타입, 탭 정의에서 파생한 `TabKey`, 도구 연동용 루트 선언 파일은 해당 구현·설정 가까이에 유지한다. React 수명 주기를 연결하는 `useQrBrightness.ts`는 기능 hook으로 유지한다. 함수 동작·타입 계약은 변경하지 않는다.

### 검토한 대안과 영향

기능별 배치를 유지하면 관련 UI와 규칙을 함께 찾기 쉽지만 이번 사용자 요청의 종류별 분리에 맞지 않는다. 별도 폴더에서는 타입·유틸리티를 한곳에서 찾을 수 있으며, 기능 소비자의 상대 import 경로가 바뀐다.

### 재검토 조건

API 응답 타입과 화면 모델을 구분해야 하거나, 유틸리티 간 의존성이 늘어나 책임별 하위 폴더가 필요해지면 배치를 재검토한다.

## ADR-003: Next.js 웹과 모바일의 공통 패키지를 구성한다

- 날짜: 2026-10-02
- 상태: 채택 — 설계 기준 채택, 런타임 구조 적용은 후속 단계
- 범위: Next.js 웹 기본 앱과 모바일·웹 공통 패키지
- 관계: ADR-002의 모바일 내부 타입·유틸리티 배치 기준을 유지하면서, 플랫폼 간 공유가 필요한 코드는 별도 패키지로 확장한다.
- 상세 설계: [Next.js 웹과 모바일 공통 패키지 설계](superpowers/specs/2026-10-02-nextjs-shared-packages-design.md)

### 배경

사용자는 기존 백엔드와 React Native 앱을 유지하고 같은 모노레포에 Next.js 웹을 추가하기로 했다. 웹은 공통 구조를 로컬에서 확인하는 기본 화면까지만 만들고, 각 단계의 변경 파일·결과·검증을 보고하며 진행한다.

공통화 도입 전 `Button`은 `PressableProps`와 네이티브 SVG 타입에, `Badge`는 React Native View·Text에 의존한다. `LocationPoint`에도 네이티브 이미지 타입이 포함돼 있어 파일을 그대로 옮기는 것만으로 웹과 공유할 수 없다. 색상 JSON과 가격 표시 함수는 플랫폼 의존성이 없으며 지점 검색은 데이터 타입 분리 후 공유할 수 있다.

### 결정

1. 루트 `api/`, `mobile/`을 유지하고 `web/`, `packages/`를 추가한다. `apps/`로 일괄 이동하지 않는다.
2. 공통 패키지는 `@iambox/contracts`, `@iambox/utils`, `@iambox/design-tokens`, `@iambox/ui`로 구분하고 필요한 소비자에서 `workspace:*`로 연결한다.
3. 공통 UI의 props·variant·디자인 규칙은 함께 관리하고 렌더링은 `@iambox/ui/native`와 `@iambox/ui/web`으로 나눈다. 처음 적용할 컴포넌트는 Button·Badge다.
4. 공통 지점 데이터에서 모바일 이미지 타입을 분리한다. 현재 mock 데이터 타입을 확정된 API 응답 계약으로 간주하지 않는다.
5. 가격 표시·지점 검색·색상은 공유한다. 바텀 시트 높이·QR 밝기·지도·앱 레이아웃·네이티브 모달은 모바일에 유지한다.
6. 웹은 Next.js App Router의 기본 화면에서 공통 UI·토큰·함수를 확인한다. 기본 개발 포트는 3001로 하고 업무 API·인증·배포는 후속 제품 작업으로 둔다.

### 검토한 대안

| 대안 | 장점 | 채택하지 않은 이유 |
| --- | --- | --- |
| React Native Web으로 같은 JSX를 웹에서도 실행 | 렌더링 코드 재사용 범위가 넓다. | 현재 NativeWind·네이티브 SVG·지도·모달 의존성을 웹 빌드와 연결하는 추가 검증이 필요하다. 기본 웹 구성에서는 플랫폼별 렌더링 경계를 먼저 분리한다. |
| 웹을 별도 저장소에서 구현 | 설치·빌드 환경을 완전히 분리할 수 있다. | 같은 서비스의 데이터·디자인 규칙을 함께 관리하려는 사용자 요청에 맞지 않는다. |
| 앱과 웹에서 컴포넌트 규칙까지 각각 관리 | 각 플랫폼 구현이 단순하다. | 공통 props·variant·색상·표시 규칙의 중복과 변경 누락이 발생할 수 있다. |

### 영향

- 웹과 모바일은 같은 공통 규칙을 사용하지만 이벤트·아이콘·접근성의 플랫폼별 처리는 각 렌더러에서 담당한다.
- 공통 규칙 변경 시 두 렌더러와 소비자의 검증이 필요하다. 같은 컴포넌트 이름이 같은 렌더링 코드를 뜻하지는 않는다.
- 패키지 이동 시 exports·import·클래스 탐색 경로·테스트 경로를 연결하고 기존 모바일 화면과 함수 동작을 보존해야 한다.
- 공유 패키지 도입만으로 업무 API, 로그인, 결제 또는 웹 제품 화면이 구현되는 것은 아니다.

### 적용 현황

1단계에서 상세 설계와 이 ADR을 작성했다. 2026-10-02의 2단계에서 기존 `mobile`, `api`에 `packages/*`를 등록하고 네 공통 패키지의 manifest·TypeScript 설정을 구성했다. `utils → contracts`, `ui → design-tokens` 내부 의존성을 연결하고 lockfile에 기록했다.

3단계에서 `LocationData`, 가격·검색 함수, 색상 JSON을 공통 패키지로 이동하고 실제 exports·typecheck를 연결했다. 모바일 지점 타입은 공통 데이터에 이미지 타입을 확장하며 기존 함수 경로는 재수출한다. 앱과 Tailwind의 색상 import는 공통 JSON subpath를 사용한다. 기존 색상과 외부 의존성 버전은 유지했다.

4단계에서 Button·Badge 공통 규칙과 native/web 렌더러를 구현하고 모바일의 기존 경로에서 native를 재수출했다. NativeWind 탐색 경로·optional native peers·플랫폼별 타입 검사를 연결했다. 웹은 전역 CSS subpath와 HTML 렌더러를 제공하며 `web/` 앱은 5단계에서 기본 확인 화면으로 생성했다. React/React DOM 19.2.3을 유지하고 로컬 3001·공통 패키지 변환·타입 검사·빌드를 연결했다. 현재 사용법은 [packages/README.md](../packages/README.md), 이전 준비 단계는 [2단계 기록](superpowers/plans/2026-10-02-shared-packages-stage2.md), 실제 코드 이동과 검증은 [3단계 기록](superpowers/plans/2026-10-02-shared-packages-stage3.md), UI 적용은 [4단계 기록](superpowers/plans/2026-10-02-shared-ui-stage4.md), 웹 연결은 [5단계 기록](superpowers/plans/2026-10-02-nextjs-web-stage5.md)을 따른다.

6단계에서 앱·API·웹 전체 타입 검사와 관련 테스트·빌드, iOS·Android export, 프로덕션 웹·iOS 공통 UI 확인을 마쳤다. 검증 범위와 기기 확인의 한계는 [6단계 기록](superpowers/plans/2026-10-02-monorepo-stage6.md)에 남겼다. 구조 도입은 완료했으며 업무 API·웹 제품 기능은 후속 범위다.

### 재검토 조건

- 실제 웹 기능에서 동일한 JSX나 복잡한 컴포넌트까지 공유할 필요가 생긴다.
- 플랫폼별 렌더러의 규칙이 달라져 공통 props나 디자인 규칙의 경계를 조정해야 한다.
- API 구현으로 현재 공통 화면 데이터와 실제 요청·응답 타입을 구분해야 한다.
- Next.js·Expo의 React 또는 빌드 요구사항이 충돌해 패키지 exports·의존성 정책을 조정해야 한다.
